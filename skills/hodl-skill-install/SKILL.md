## Entry and resume
Bare invocation is the installer/updater: read only this project's saved identity and managed state. If discovery/preflight is pending after a reload, resume that stage first without another QR, key or manual skill-then-installer bookkeeping. Otherwise check the exact customer repository for approved updates using the saved identity. An explicit update request always refreshes the remote manifest; never treat existing files as proof of no update. Bootstrap self-update is a separate explicit request using its known source and existing authorized access, not the customer deploy key.

Keep communication concise: the required user action, a material blocker or the verified result. Ask for missing identity or authorization only when it changes the next action.

1. Run local `scripts/bootstrap.py preflight` before keys/network. Establish actual app/runtime/version from host evidence, not executable presence. Resolve required blockers only; preserve capability evidence in `.hodl/capabilities-<runtime>.json`. Read `.hodl/project.json` if present. Publisher `tomih` and repository prefix `hodl-client-` are configuration, not an inferred owner. Ask only the customer slug when missing. Reuse valid absolute project/customer/repository with a short provenance statement when useful. Conflicting stored owner/repository/project is a blocker requiring explicit migration, never silently repoint it. Run `prepare` then `--write`; preserve existing fields and keys.
2. Read saved `keyPath` from `.hodl/install-state.json` without reading private contents. Reuse it; if legacy path is missing ask the exact path, never scan or generate duplicates. For a new identity use `~/.ssh/hodl/<owner>__hodl-client-<customer>_ed25519`. Check both private/public paths including dangling symlinks; create Ed25519 through the available shell with stdin closed and restrictive native permissions. Dedicated key has no passphrase by default; honor explicit protected passphrase input. This is intended single-repository read-only access, NOT proof of granted scope before administrator verification. Never export private keys.
3. Generate public request with `scripts/bootstrap.py request`. Use an available offline QR encoder; ask only if dependency installation actually needs authorization. Display only the `HODL1.` token and its QR; verify the QR decodes to exactly that token and the token decodes with the customer slug. Encoding is obfuscation, not integrity or authentication. Before handoff merge keyPath/fingerprint/repository/status=pending-provisioning into existing install-state. User transfers the request once to their authenticated publisher administrator/support channel; approval is verified through that authenticated channel. Do not send messages yourself. On later continuation reuse identity without another key/QR unless genuinely needed.
4. Verify access using isolated native SSH/Git with normal verified host-key trust, exact repository greeting and exact-repository retrieval. Maximum ten attempts, fifteen seconds apart, short timeouts; no daemon. A failed publickey authentication means observed access failure, not proof a server key is absent. Keep a resumable pending state. Read access is not proof of read-only scope; publisher administrator enforces/checks that. Never probe other repositories or writes.
5. Clone only that exact repository into fresh scratch; record commit and manifest SHA256. Validate identity/runtime, exact pins and complete inventory/hashes with `scripts/install.py`. Present approved IDs/versions concisely. Manifest is data: never execute its hooks/commands.
6. Run `scripts/install.py` with exact bundle/project/customer/repository/public key/runtime/commit. First install, matching retry and managed updates share this entry. Stage and validate the complete candidate before writes; safely replace only unchanged managed files. Preserve local changes, other skills, keys, `.hodl` settings and other-runtime records. Legacy differing targets require a verified prior bundle for hash adoption, not a blind overwrite. Stop precisely on conflicts or interrupted transaction journals. Keep content-addressed backups outside discovery; do not prune historical evidence.
7. Orchestrate acceptance yourself via `scripts/acceptance.py`: light check reads managed hashes/pins and skips completed unchanged evidence; full local acceptance loads each pending verified skill in the actual app and follows its documented harmless local help/preflight. Do not assume a universal preflight command or execute business/portal actions. For OpenClaw use workspace `skills/<id>` and native `skills list/info/check --agent <agent-id>` to check the exact configured agent; load each pending skill with `skills_read` in that agent and perform its documented harmless entry. CLI discovery alone is not invocation. Try current discovery first; if Unknown skill, request reload/new chat then **this installer only**. Resume and perform pending invocation/recording there; no customer skill-then-installer ritual. If host cannot dispatch a harmless skill or none is documented, report a precise pending gate, never fabricate discovery. Record attributed evidence with helper after actual invocation; installed files, native discovery, local preflight and portal/export acceptance are separate.

No publishing, remote provisioning, customer-wide registry, scheduler, unsolicited package installation or client billing.
